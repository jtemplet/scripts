YOUR TASK
═══════════════════════════════════════════════════════
Review the diff between this branch and main. Then fix any issues you find.

    cd {worktree}
    git diff main...{branch}

Things to look for — be thorough:

  • Correctness — Does the code actually do what the description says?
  • Bug risk — Off-by-one, null/nil handling, race conditions, edge cases?
  • Security — Any injection vectors, unvalidated input, exposed secrets, unsafe deserialization?
  • Performance — N+1 queries, unbounded loops, missing indexes for new DB columns?
  • Maintainability — Are functions too long? Are things named clearly? Is the code testable?
  • Test coverage — Does the test suite actually exercise the new code paths? Are assertions meaningful?
  • Consistency — Does this code follow the patterns already established in the rest of the repo?
  • Docs — If this is a user-facing feature or a public API, is it documented?

If you find problems, fix them directly in the worktree. If the issues are minor and the code is fundamentally sound, fix and move on. If the code is fundamentally broken or the approach is wrong, fix it — do not just flag it.

After fixing, run the test suite one more time to make sure everything still passes.

═══════════════════════════════════════════════════════
WHEN YOU ARE DONE — DO THESE STEPS IN ORDER, EXACTLY
═══════════════════════════════════════════════════════

    cd {worktree}
    git add -A
    git commit -m "review({bead_id}): code review fixes" --allow-empty

    cd {repo_root}
    br label remove {bead_id} in_code_review
    br label add {bead_id} ready_for_qa

The --allow-empty flag is intentional: if the code was already clean and you made no changes, the commit still needs to happen so the pipeline knows you finished. Do not skip it.

Do not close the bead. Do not change the br status. Do not merge anything.
